# 02. Unreal Engine での実現構成案

> 状態：**提案**（プロトタイプで検証して確定させる）

## 1. 全体方針：「街＝共有ワールド」＋「探索＝インスタンス」

UE標準の専用サーバーは、1プロセスあたり**数十〜100人程度**が現実的な上限です。
MMOのような「全員が1つの巨大ワールド」は個人開発の規模では技術的・費用的に困難なため、次の構成を提案します。

```
                 ┌──────────────────────────┐
                 │ バックエンド（自作API + DB）│
                 │ ・アカウント/キャラ保存      │
                 │ ・インベントリ/通貨（正本） │
                 │ ・市場/取引/家賃/許可証      │
                 └─────┬───────────┬────────┘
                       │            │
        ┌──────────────┴─┐   ┌────┴──────────────┐
        │ 街サーバー       │   │ 探索サーバー          │
        │ (共有・常駐)     │   │ (パーティごとに起動)  │
        │ 30〜80人         │   │ 1〜4人 + モンスター   │
        │ ギルド/市場/住宅 │   │ 狩猟/剥ぎ取り/搬送    │
        └────────────────┘   └───────────────────┘
```

この構成は本作の仕様と相性が良いです。

- **許可証による探索時間制限** → 探索サーバーの寿命と一致させられる
- **持ち帰り・帰還期限** → 探索終了時にサーバーがバックエンドへ結果を確定保存
- **搬送の協力プレイ** → パーティ単位のインスタンス内で完結
- **街での交流・経済** → 共有サーバー＋バックエンドで一元管理
- **個人ストーリーと共有世界の両立** → 探索インスタンスは個人/パーティの進行度で内容を変え、街は「共通部分＋個人フラグによる表示差分（フェージング）」で対応

## 2. 採用する技術（すべてUE標準または無料）

| 領域 | 採用技術 | 理由 |
|---|---|---|
| 言語 | **C++（土台）＋ブループリント（調整・演出）** | 通信・ゲームロジックはC++で堅牢に、数値やエフェクト調整はBPで素早く |
| 入力 | Enhanced Input | UE5標準 |
| キャラ移動 | Character Movement Component | 通信同期・予測補正が組み込み済み |
| 戦闘・能力 | **Gameplay Ability System（GAS）** | 攻撃・回避・状態異常・属性・武器固有能力をサーバー権限で管理でき、マルチプレイ対応済み。学習コストは高いが長期的に最も安い |
| モンスターAI | Behavior Tree または StateTree ＋ EQS | 攻撃パターン・索敵 |
| 部位破壊 | 物理アセットのボーン単位ヒット判定＋部位HP（自作） | 剥ぎ取り・搬送の部位素材と直結 |
| 荷車・車両 | Chaos Vehicles（標準プラグイン）＋自作の牽引ロジック | 荷車・馬車は物理を簡略化した自作が安定する可能性あり（要検証） |
| UI | UMG ＋ Common UI | パッド対応 |
| ワールド | World Partition ＋ PCG（手続き生成） | 自然環境を少人数で量産 |
| データ定義 | Data Asset / Data Table（CSV取り込み可） | モンスター別報酬表・レシピ・職業をコードを触らず追加 |
| オンライン基盤 | Epic Online Services（無料） | ログイン・フレンド・ロビー |
| バックエンド | 自作API（例：Go または TypeScript）＋ PostgreSQL | 通貨・アイテムの正本をサーバーDBで管理。Claude がクラウド上でも開発・テストできる部分 |
| サーバー運用 | 開発中：自分のPC → テスト：安価なVPS → 本番：需要に応じてクラウド | 初期費用を最小化 |

## 3. 不正対策の基本ルール（初期から守る）

1. **クライアントは「入力」を送るだけ**。ダメージ・ドロップ・所持金の計算はすべてサーバー。
2. アイテム・通貨の増減は**バックエンドのDBトランザクション**で確定（二重取得・複製の防止）。
3. 取引・市場は「サーバーで検証 → DB確定 → 結果を通知」の順。
4. 探索結果は探索サーバーがまとめて送信し、バックエンドが妥当性（重量上限・時間・出現モンスター）を検証。
5. 装備制限（レベル・ストーリー進行）はサーバー側で判定。

## 4. 主要システムのデータ設計の考え方（拡張性重視）

- **アイテム**：`ItemDefinition`（種類・重量・カテゴリ）と `ItemInstance`（品質・耐久・製作者・特殊性能）を分離。製作者の職業や素材品質を個体に記録できる。
- **モンスター報酬**：モンスターごとに「剥ぎ取り表」「部位搬送表」「全体搬送表」をデータで持つ。計算式は共通、数値はデータ側。
- **搬送**：死体を `Carcass`（部位ごとの状態・重量・劣化時間）として扱い、剥ぎ取り/切り出し/丸ごと積載をすべて同じデータから処理。
- **職業**：職業ごとの「個人効果」と「パーティ効果」をGASの効果（Gameplay Effect）として定義。
- **ストーリー/勢力**：プレイヤーごとのフラグと勢力評価値をバックエンドに保存。共有世界の変化は「サーバー全体イベント」として別管理。

## 5. 段階ごとのサーバー構成

| 段階 | 構成 | 費用 |
|---|---|---|
| 第1〜2段階 | エディタ内でサーバー＋クライアント複数起動（PIE） | 0円 |
| 第3〜5段階 | 自分のPCでソースビルド版の専用サーバーを起動、友人とテスト | 0円 |
| 第6〜7段階（ベータ） | VPS/クラウドに街サーバー1台＋探索サーバー数台＋DB | 月数千〜数万円程度（人数次第・要見積もり） |
